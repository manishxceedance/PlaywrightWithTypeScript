Week 2, Day 5: Actions, Transactions, Pages, and Requests

Session outcome

Learn how NeoLoad organizes a recorded journey into business-readable actions, measurable transactions, page boundaries, and technical requests. You will apply the structure to the HRMS login, employee search, edit, save, and logout path from Day 4.

A well-structured user path makes results easier to read, helps teams connect performance data to business activity, and prevents a report from becoming a long list of anonymous HTTP calls.

1. The four levels of a NeoLoad user path

LevelMeaningPerformance purpose
ActionA user intention or interaction, such as entering search criteria or selecting Save.Explains what the virtual user is doing and keeps the flow readable.
TransactionA measured business operation containing one or more actions and requests.Produces a business-level response-time and success measurement.
PageA logical navigation or screen boundary, such as Login, Employees, or Edit Employee.Groups related activity and helps locate slow parts of a journey.
RequestA technical network operation, such as an HTTP request, resource call, or API call.Shows the protocol-level work that creates the page or completes the action.

The levels are related but are not interchangeable. A request is not automatically a business transaction, and a button click is not automatically a useful performance measurement.

2. Actions: describe user intent

An action describes a meaningful step performed by a virtual user. It should answer, “What is the user trying to do?” Actions can include opening a page, entering a search value, selecting a record, submitting a form, waiting for a result, or logging out.

Good action names

  • ACT_OpenEmployees
  • ACT_SearchFirstEmployee
  • ACT_OpenEmployeeEdit
  • ACT_UpdateTrainingNote
  • ACT_SubmitEmployeeChanges
  • ACT_Logout

Action design rules

  • Use a verb and an object: SearchEmployee is clearer than Step3.
  • Represent user intent, not an arbitrary browser event.
  • Keep one action focused enough to troubleshoot when it fails.
  • Do not create an action for every static image, stylesheet, or browser housekeeping call.
  • Keep sensitive values out of names, comments, screenshots, and exported projects.

3. Transactions: measure business operations

A transaction is the unit that stakeholders usually care about. It starts before a business operation and ends after the expected result has been received and validated. The measured time should represent the user-visible operation, not an arbitrary fragment of the recording.

Recommended HRMS transactions

TransactionStartEndSuccess check
TRX_LoginSubmit the login form.Dashboard is available.Dashboard or authenticated state is visible.
TRX_OpenEmployeesSelect Employees.Employee table is loaded.Table and result count are available.
TRX_SearchFirstEmployeeEnter the first record value.Filtered row is displayed.Expected employee row is present.
TRX_SaveEmployeeSubmit the edit form.Save response and UI confirmation complete.Success message or refreshed value is visible.
TRX_LogoutSelect Logout.Login page is displayed.Authenticated dashboard is no longer accessible.

Do not make one transaction cover the entire journey if you need to know which business step is slow. You may keep a broad end-to-end transaction as an additional measurement, but retain useful child transactions for diagnosis.

4. Pages: create meaningful boundaries

A page groups the requests and actions associated with a logical screen or navigation state. Pages help you read a user path from left to right and compare the time spent entering or leaving a screen.

For the HRMS scenario, useful page boundaries are:

  1. PAGE_Login: login document, scripts, session establishment, and dashboard redirect.
  2. PAGE_Dashboard: dashboard data and initial widgets.
  3. PAGE_Employees: employee table, filters, pagination, and list data.
  4. PAGE_EditEmployee: edit modal data and update form resources.
  5. PAGE_Logout: logout request and return to the login state.

A page boundary should be stable across recordings. Avoid naming a page after an unstable generated ID unless that ID is a data value documented separately.

5. Requests: understand the technical work

Requests are the lowest-level technical units visible in a web recording. They may retrieve HTML, JavaScript, CSS, images, employee data, search results, session information, or update data.

Request naming convention

Use a consistent pattern such as REQ_[Method]_[Purpose]:

  • REQ_GET_LoginPage
  • REQ_POST_Login
  • REQ_GET_Employees
  • REQ_GET_SearchEmployees
  • REQ_GET_EmployeeDetails
  • REQ_PUT_UpdateEmployee
  • REQ_POST_Logout

Keep a request when it contributes to the user journey, authentication, dynamic data, business validation, or a monitored dependency. Remove a request only after confirming that it is noise and does not change application behavior.

7. Practical NeoLoad activity

  1. Open the Day 4 user path UP_HRMS_Search_Edit_Logout.
  2. Review the recorded tree from the top down. Mark each item as action, transaction, page, request, or noise.
  3. Create the five business transactions listed above and place each around the complete business operation.
  4. Create or rename page boundaries for Login, Dashboard, Employees, Edit Employee, and Logout.
  5. Rename the important requests using the REQ_[Method]_[Purpose] convention.
  6. Keep the existing correlation variables from Day 4 and ensure dynamic values are not replaced with new hard-coded values.
  7. Replay with one virtual user and confirm that every transaction has a meaningful result.
  8. Review the result view and confirm that you can identify login, employee search, update, and logout timings without reading anonymous request names.

8. Common mistakes

  • One transaction around the entire script: useful for total time, but insufficient for finding the slow business step.
  • One transaction per request: creates noisy reports and hides business meaning.
  • Page names contain generated values: reports become difficult to compare between iterations.
  • Static resources are treated as business work: response-time measurements become harder to interpret.
  • Assertions are omitted: a fast error can be reported as a successful transaction.
  • Correlation is removed while renaming: the script may work once and fail for another user or iteration.

Submit an annotated UP_HRMS_Search_Edit_Logout tree showing actions, five transactions, page boundaries, and named requests. Include one successful one-user replay and a short explanation of why each transaction boundary was selected.
