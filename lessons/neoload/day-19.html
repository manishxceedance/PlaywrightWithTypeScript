Week 7, Day 19: Percentiles, Throughput, Errors, and User Count

IntermediateRead the actual experience of the system, not just the average measurement.

Session outcome

Many teams look at a single average response time and think they understand the result. This day teaches the important metrics that explain the shape of a run: percentiles, throughput, error behavior, and active user count. These are far more informative when judging whether the system met the workload objective.

1. Percentiles

Percentiles show how the response times distribute across all measured transactions. They are especially important because averages can hide poor tail performance.

  • p50: median response time, where half of the requests are faster and half are slower.
  • p90: 90% of requests are faster than this value; the tail starts to appear.
  • p95: widely used in service-level analysis because it reflects the slower experience of a substantial group of users.
  • p99: extreme slow responses; useful for understanding tail latency or rare but severe issues.

If p95 rises sharply while p50 stays stable, the problem may be concentrated in the slower tail rather than the “typical user” experience. This is why a single average can be misleading.

2. Throughput

Throughput tells you how much work the system completed during the run. It is often measured as transactions per second or requests per second. This metric answers, “How much useful work was the system able to complete under the applied load?”

Throughput and response time are connected: a system may handle high load but with increased latency, or it may remain fast but process less work. Both can be true at the same time depending on the bottleneck.

3. Error rate

Errors show whether the system remained valid under the applied workload. An error rate can directly affect application trust and user value. It is often more important than a low average response time if the system is returning incorrect results or rejecting too many requests.

When reviewing errors, always ask:

  • Which transactions failed?
  • When did the failures start?
  • What was the error type or message?
  • Was the failure associated with a specific load zone or time window?

4. User count

Active users show the real load pressure imposed on the system. A performance result is not just “successful” because the script ran; it needs to be tied to the user count relevant to the target scenario. Without the user count, it is difficult to judge whether the result reflects a realistic or unrealistic workload.

When comparing results, make sure you compare the same percentage of load, the same duration, and the same user mix. Otherwise, differences in response time or throughput may be simply due to a different workload profile.

5. Reading result tables correctly

When reviewing a report, do not isolate a single statistic. Instead, read them together:

  • p50, p95, and p99 show the range of response experience.
  • Throughput shows how much useful work the system completed.
  • Errors show whether correctness stayed stable.
  • User count shows the applied load.

A useful question is: “How did the system behave as user count increased?” This is far more informative than a single point-in-time average.

Day 19 deliverable

Prepare a one-page metric summary for one result set using p50, p90, p95, p99, throughput, error rate, and active user count. Explain how the metrics changed between the low-load and peak-load phases.
