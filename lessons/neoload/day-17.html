Week 6, Day 17: Runtime Health, Errors, and Server Metrics

IntermediateWatch the live system as load changes and keep evidence grounded in observed behavior.

Session outcome

During execution, NeoLoad provides response time and transaction data, but the server and application health also matter. This day focuses on runtime observation: how to read the system while it is under load and how to avoid jumping to conclusions before the evidence is connected.

1. What to monitor during a run

When the workload is active, monitor the variables that describe user experience and environment health. The most common areas are:

  • Response time and transaction timing: are key business operations growing slower?
  • Error rate: are failures beginning to appear or rising sharply?
  • CPU utilization: is a tier saturating or becoming overloaded?
  • Memory usage: is the application leaking memory or approaching a dangerous threshold?
  • Network and database latency: are backend dependencies becoming the constraint?
  • Application logs: are there warnings, retries, or exceptions around the same time as a slowdown?

Monitoring is most valuable when it is connected to the time window of the workload. You need timestamps and run phases to align user behavior and system behavior.

2. The value of time correlation

One of the most common mistakes in performance analysis is to say, “The database looks high, so it must be the cause,” without checking whether the same time window has production traffic, increased error rate, or higher concurrency. The correct approach is time correlation.

Look across the same timeline:

  • When did transaction response time begin to rise?
  • When did the error rate climb?
  • When did CPU or memory peak?
  • What happened in the app logs at the same moment?

This makes the analysis defensible. It creates a chain of evidence rather than a single suspicious metric.

3. Runtime health signals

During runtime, several signals deserve attention:

  • Rising p95 or p99 values on critical transactions.
  • Rising error count or error rate over a sustained period.
  • Queue buildup, thread exhaustion, or saturation.
  • GC or memory pressure in application server logs.
  • Database lock, deadlock, or increasing latency patterns.

A single rising metric is not enough to prove a bottleneck. It is only a clue. The complete analysis requires more context and a clear comparison against baseline or expected operating behavior.

4. Monitoring snapshot approach

Capture a monitoring snapshot at multiple phases of the run:

  1. Start of the run.
  2. Steady state or early hold period.
  3. At the point where the system is under increasing load.
  4. At the end or near stop condition.

This makes it easier to compare “normal” to “under stress” and prevents the run from being described with only a single peak or one generic screenshot.

6. Common mistakes

  • Claiming a bottleneck without matching timestamps: correlation is essential.
  • Ignoring logs: application logs often explain why the server slowed or rejected work.
  • Looking only at averages: percentiles and outliers often reveal tail problems.
  • Reporting a single metric as the cause: system health must be reviewed as a set.

Day 17 deliverable

Capture a runtime observation sheet with timestamps for at least three phases of the run: start, steady state, and peak or near-stop state. Include key response-time signs, error observations, and at least two server-health indicators.
