Week 8, Day 23: Baseline Versus Load-Test Execution

CapstoneRun the test with control, consistency, and evidence retention.

Session outcome

This day brings together all the prior work: script validation, workload design, data handling, monitoring readiness, and go/no-go decisions. The goal is to execute both a baseline and a target workload in a way that supports a legitimate comparison and a defensible final result.

1. Baseline execution

A baseline run is the low-to-moderate workload that acts as a comparison point. It should be smaller than the target workload, but still realistic enough to show how the application behaves under stable conditions.

During the baseline, confirm:

  • The script runs successfully.
  • Transactions and assertions behave as expected.
  • Monitors record the main health signals.
  • Environment conditions match the approved test plan.

Baseline results are not “just a warm-up.” They are a critical control run used later to compare the target workload and identify regressions or shifts in performance.

2. Target-load execution

After the baseline is approved, run the target workload with the agreed ramp, hold, and stop conditions. Keep the same script, workload assumptions, and data pattern unless the approved plan explicitly calls for a change. That consistency is what makes the comparison meaningful.

During the run, document:

  • When the load increased.
  • When the system began to show signs of degradation.
  • Any warnings, errors, or abort decisions.
  • Whether the run stayed within the agreed scope.

3. Execution log and artifacts

Both runs should be stored with enough metadata that another reviewer can understand the environment and conditions. Capture:

  • Project and script version
  • Build, environment, and date
  • Workload, ramp, and user count
  • Monitoring exports or screenshots
  • Warnings or operational notes
  • Final run status and stop reason if applicable

Without these artifacts, a reviewer cannot judge whether the comparison is meaningful or whether an anomaly was caused by test design rather than the application itself.

4. Common mistakes during execution

  • Changing the script between baseline and target run.
  • Starting the target load without a valid smoke check.
  • Ignoring operational notes or warnings during the run.
  • Not preserving the correct artifacts for comparison.
  • Changing the environment or data unexpectedly and then comparing results as if they were identical.

Day 23 deliverable

Submit two labeled result sets: baseline and target load. Include the execution log, the workload conditions, the environment used, and any warnings or deviations that occurred during the run.
