Week 4, Day 12: JSON Extraction and Positive/Negative Checks

IntermediateValidate both the data contract and the error behavior behind the API.

Session outcome

This day is about correctness under both success and failure conditions. You will learn to read JSON responses precisely, extract the right values, and write checks that prove the API handles valid and invalid requests according to its contract.

1. Why JSON extraction matters

Many modern APIs return structured JSON. A response may include metadata, a token, a list of objects, a created record ID, or an error object. If you only inspect the status code, you may miss the most important business fact: did the server return the correct data, or did it return a generic success with the wrong payload?

Stable JSON extraction is the foundation of chained, data-driven API testing. For example:

  • Login response includes token or sessionId.
  • Employee create response includes the new id.
  • Get employee response includes status or name.
  • Error response includes message or errorCode.

In NeoLoad, extraction gives you a reusable variable that can be fed into later requests. This is what makes an API flow realistic and maintainable.

2. JSON path discipline

When extracting from a JSON response, you need a path that is stable and specific. Common examples include:

  • $.token
  • $.data.id
  • $.user.name
  • $.items[0].employeeId

If the structure is nested or the response contains arrays, be precise. A broad extractor can capture the wrong value. A good extractor is specific to the real contract and easy to reason about.

Also consider that JSON field names may change or not always be present. A response may include data, results, or a top-level object with a nested list. You must validate the structure before writing the final assertions.

3. Positive checks

Positive checks confirm that a valid request behaves as expected. This is where you prove that the script is not just making a call, but demonstrating the business outcome. Examples:

  • Valid login returns 200 and a valid token.
  • Employee lookup returns the correct employee name.
  • Update request returns 200 and the changed field value matches the request.
  • Create request returns 201 and the ID is not null.

These checks should be tied to the business requirement. A record’s response must be meaningful, not just non-empty.

4. Negative checks

Negative checks confirm that invalid input fails in a controlled and documented way. This is especially important for API behavior because real users make mistakes and systems must react predictably.

Typical negative scenarios include:

  • Invalid credentials return 401 or a failure message.
  • Missing required field returns 400 with a validation message.
  • Unauthorized access returns 403 or equivalent.
  • Unknown ID returns 404 and does not create or mutate a record.

A negative check does not just “show an error.” It proves the API responds consistently and does not produce a wrong side effect.

5. The validation matrix

Before running your script, write a small table with each request, success check, negative check, and evidence. Example:

The matrix makes your load test more trustworthy. It also helps when failures occur: if a script fails only on the invalid scenario, you know the problem is in validation or request handling rather than the general workflow.

6. Practical exercise

  1. Pick one authenticated API flow with at least one success and one error path.
  2. Inspect the JSON response for the data fields needed to build a later request.
  3. Extract a value such as token, id, or status using a stable JSON path.
  4. Write one positive assertion and one negative assertion for the same business action.
  5. Replay both scenarios and save the evidence showing the expected behavior.

7. Common mistakes

  • Matching text instead of values: free text messages change often and make tests brittle.
  • Only checking one part of the JSON structure: a nested object may still be wrong.
  • Not checking failure states: the script looks green while invalid input is silently accepted.
  • Using a stale token or ID in later requests: the chain is broken but the status code may still look valid for the wrong reason.
  • Ignoring the difference between business and technical success: not every 200 indicates a correct business action.

Day 12 deliverable

Submit an API validation sheet with one successful request path, one extracted JSON value, one positive assertion, and one negative assertion with the expected response and evidence. Include the exact value source and the JSON path used for extraction.
