Week 2, Day 4: Record the HRMS Web User Path

Scenario and objective

Record one complete HRMS employee-maintenance journey: sign in, open Employees, search for the first employee record, edit a safe training field, save the record, and log out.

Use the published Login - HRMS Practice App. Use only the approved training account and approved test data for your environment.

Important: This is a functional recording with one virtual user. Do not increase load until the path is validated and the data-change strategy is approved.

1. Prepare the recording

  1. Open NeoLoad and the neoload-training project created on Day 3.
  2. Start a new web recording and name the user path UP_HRMS_Search_Edit_Logout.
  3. Use the published HRMS login URL as the recording start page.
  4. Confirm that the target environment, test account, and record-edit permission are approved.

2. Record the HRMS journey

  1. Open the HRMS login page and complete the sign-in form with the approved training account values.
  2. Wait until the dashboard is visible. Add a transaction named TRX_Login.
  3. Open Employees from the navigation or use View Employees. Add TRX_OpenEmployees.
  4. Wait for the employee table to finish loading. Do not use a fixed sleep if a visible table or result count can be observed.
  5. Identify the first row in the employee table. Capture its displayed employee name or employee ID as a runtime value for later correlation.
  6. Enter that value in Search by name, email, ID, title... and wait for the debounced results to refresh. Add TRX_SearchFirstEmployee.
  7. Click the Edit action for the matching row and add TRX_OpenEdit.
  8. Change one approved, reversible training field, such as the notes field. Do not alter identity, access, salary, or compliance data unless your instructor explicitly approves it.
  9. Click Save Changes. Add TRX_SaveEmployee and verify the success notification or refreshed row.
  10. Click Logout and add TRX_Logout. Confirm that the login page is displayed again.
  11. Stop the recording and save the user path.

3. Clean and organize the recorded path

  • Remove analytics, static assets, browser noise, and unrelated third-party requests only when you understand their purpose.
  • Keep requests needed to create the session, load employee data, search, update the record, and log out.
  • Rename pages and requests so another tester can understand them, for example REQ_GetEmployees, REQ_SearchEmployees, and REQ_UpdateEmployee.
  • Keep the transaction boundaries aligned with business actions rather than individual clicks.
  • Replay the path with one virtual user and confirm the saved change and logout are successful.

4. Why the path fails without correlation

A recording captures the values returned during one browser session. Some of those values are generated dynamically and will be different in another session, another iteration, or another virtual user. If the script replays the original values literally, the server may reject the request or update the wrong record.

Dynamic valueWhy it changesWhat to correlate
Session or authentication valueCreated for a new sign-in session.Extract the value from the login response or session flow and reuse it in later requests.
Employee IDThe first row, search result, or selected record may have a generated identifier.Capture the identifier from the employee list or search response before the edit request.
CSRF or request tokenSecurity tokens can be generated per page or session.Extract the token and pass the current value in the update request.
Record version or update timestampOptimistic-locking data can change after a read.Capture the latest version value and send it with the save operation when required.

5. Demonstrate the no-correlation failure

  1. Replay the recorded path once with one virtual user and save the successful result.
  2. Inspect the request that searches for or updates the employee record. Identify recorded values that came from an earlier response.
  3. Run a controlled second iteration with the recorded values left unchanged. Capture the first failure, status, response message, and timestamp if the application rejects stale or invalid values.
  4. Do not keep retrying a failed update against shared data. Restore the approved training value if the first run changed it.
  5. Document whether this application exposes the value in an HTTP response, browser storage, a cookie, or only through client-side IndexedDB.

Application-specific challenge: the HRMS practice app uses browser-side session and data storage. Some browser operations may not appear as ordinary server API requests in a NeoLoad recording. If the employee identifier or update is handled entirely in client-side storage, explain that limitation and record the visible browser flow separately rather than claiming that HTTP correlation has been demonstrated.

6. Correlation strategy

  1. Run the path and locate the dynamic value in the response or captured browser data.
  2. Add the appropriate NeoLoad extractor or variable for the value.
  3. Replace the recorded literal with the extracted variable in every later request that consumes it.
  4. Replay with one user, then repeat with a second approved data set or iteration.
  5. Verify that the update affects only the intended training record and that logout still succeeds.

Day 4 deliverable

Submit the cleaned UP_HRMS_Search_Edit_Logout user path, a transaction map, one successful one-user replay, a no-correlation failure observation, and a correlation decision log listing each dynamic value, its source, and its intended handling.

Common recording problems

  • Login works but later requests fail: inspect session values and tokens before changing the workload.
  • Search returns no row: wait for the table and debounce refresh, then use the displayed first-row value rather than a hard-coded guess.
  • Save updates the wrong record: stop immediately, restore approved data, and correlate the employee identifier.
  • NeoLoad shows no employee update request: document the client-side storage limitation; the browser workflow may not be represented as HTTP traffic.
  • Logout is not recorded: confirm the session is still valid and retain the logout action as a business checkpoint.
