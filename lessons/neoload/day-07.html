Week 3, Day 7: Variables, Scopes, and Data Parameterization

IntermediateReplace static constants with controlled, reusable data.

Learn

In real performance tests, hard-coded values break quickly. A login, search, order, or API request often needs values that change by user, iteration, or environment. Variables let you store and reuse these values safely. Scope decides where a variable is valid, and parameterization decides how it is populated across virtual users and test runs.

Variables

Variables hold values such as usernames, search terms, product IDs, session tokens, or dates. They should have clear names and a single purpose. Example: userName, searchText, orderId.

Scopes

Scope controls the lifetime and visibility of a variable. A value may be unique per virtual user, shared across a transaction, reused for all users in a test, or set from a runtime context. Choosing the correct scope avoids accidental data leakage and makes debugging easier.

Parameterization

Parameterization feeds one scenario with many realistic values from a data file or variable source. This lets you test multiple users, search terms, account types, or product catalogs without changing the script itself.

Typical scope choices

  • Per user / virtual user: username, password, customer ID, session-specific state.
  • Per transaction: request-specific values like order quantity, selected product, or dynamic filter value.
  • Global: environment URL, test run name, or shared configuration.
  • Runtime-derived: values extracted from a response such as tokens, page IDs, or form IDs.

Good practice: keep variables descriptive, avoid mixing responsibilities, and do not store secrets in plain text if logs or reports are exposed. Mask sensitive fields and restrict access to approved data sets.

// Example: variable names and usage
userName = ${userData.username}
searchTerm = ${data.searchTerm}
productId = ${product.id}

// Scope examples
- User scope: login credentials
- Transaction scope: order quantity
- Global scope: base URL

Do

  1. Create a small data file with at least five rows of realistic test data.
  2. Parameterize at least three values in your script, such as username, search term, and product ID.
  3. Run the scenario with more than one record and confirm the requests change per data row.
  4. Document the variable name, source, scope, lifetime, and masking rule in a short data dictionary.

Deliverable

A parameterized test script plus a data dictionary with columns for Variable, Source, Scope, Lifetime, and Masking / Security Rule.

Example data dictionary

Variable Source Scope Lifetime Masking Rule
userName CSV file Per user One user session Use approved test account only
searchTerm CSV file Transaction Single request Log safe values only
baseUrl Global variable All users Whole test run No secrets; environment-specific

Checkpoint: If a value changes across users, it should usually be parameterized. If it stays constant for the entire run, it can stay global. If it is created during the run, it should likely be captured as a runtime variable.
