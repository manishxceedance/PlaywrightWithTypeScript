Week 7, Day 21: Time Correlation and Bottleneck Hypotheses

IntermediateTurn measurements into testable explanations tied to the system’s behavior over time.

Session outcome

Performance analysis is not about naming the first suspected cause. It is about connecting time-series evidence to a hypothesis that can be tested. This day teaches how to correlate load, transaction response time, errors, and server metrics so the conclusion is evidence-based rather than guess-based.

1. The difference between a symptom and a bottleneck

A symptom is something you observe in the results, such as high response time or a rising error rate. A bottleneck is a system constraint that plausibly explains the observed behavior. A well-written bottleneck hypothesis is a structured explanation, not a casual guess.

Example: “The login transaction begins to fail under peak load while database CPU rises sharply and error messages indicate connection exhaustion” is a stronger statement than “the database is slow.” The first is evidence-based and tied to the time window.

2. Time correlation process

To test a bottleneck hypothesis, compare the relevant metrics across the same time range:

  • When did the business transaction start to degrade?
  • Did user count or arrival rate increase at the same time?
  • Did server CPU, memory, or database latency rise around the same moment?
  • Did logs or errors appear in the same phase?

If these metrics align in time, the hypothesis has more evidence. If they do not, the explanation should be treated as weaker or discarded.

3. Typical bottleneck categories

  • Database saturation: database CPU, lock waits, query latency, or queue buildup.
  • Connection exhaustion: thread pools, connection pools, or request limits reached.
  • Downstream dependency latency: API or service calls becoming slower or timing out.
  • Memory or garbage-collection pressure: rising memory use and slower processing.
  • Network or infrastructure saturation: throughput or latency growth at a platform layer.

These are not always mutually exclusive. In real systems, a bottleneck may surface in one layer and trigger a second problem elsewhere. The analysis should remain disciplined and evidence-first.

4. How to write a bottleneck hypothesis

A strong hypothesis includes:

  • Suspected constraint: database, thread pool, app server, network, or dependency.
  • Evidence: metrics or logs showing the issue aligns with performance change.
  • Confirming signal: what would confirm the hypothesis?
  • Disconfirming signal: what would weaken or disprove it?

Example: “The update employee flow slows as database CPU climbs during peak load. A confirming signal would be rising DB wait times and query latency. A disconfirming signal would be stable DB metrics while app-server CPU and queue depth climb.”

5. Practical exercise

  1. Choose one slow transaction from the result set.
  2. Write three bottleneck hypotheses related to different system layers.
  3. List one confirming metric and one disconfirming metric for each.
  4. Mark which hypothesis is strongest based on the current evidence.

Day 21 deliverable

Submit a bottleneck hypothesis log with the transaction under review, three hypotheses, evidence used to support each, and the confirming/disconfirming signal you would use to validate or reject each hypothesis.
