Week 8, Day 24: Evidence, Limitations, and Recommendations

AssessmentClose the test cycle with a result that can be reviewed, questioned, and trusted.

Session outcome

The final step in performance testing is not “present the graph.” It is to write a report that separates facts from interpretation, states the limitations of the test, and provides practical recommendations. This day focuses on communicating a conclusion that is evidence-based and understandable to both technical and non-technical reviewers.

1. What should be in the final report

A strong performance report usually includes:

  • Objective and scope of the test.
  • Workload model and user mix.
  • Environment, data, and script version.
  • Baseline versus target-load comparison.
  • SLA results and metric summary.
  • Errors and their timing.
  • Monitoring evidence and suspected constraints.
  • Limitations and caveats.
  • Recommendations and next actions.

The report should tell the reader not only what happened, but also the reason the conclusion is credible.

2. Separate facts from interpretation

Good reporting is careful about what is observed and what is inferred.

  • Observed fact: p95 login response time increased from 1.2s to 3.8s at the target workload.
  • Interpretation: the login flow is likely bottlenecked by the application tier or downstream dependency.

The first is directly supported by the data. The second is a hypothesis that should be described as such, with the evidence that supports it and the gaps that still remain.

3. Limitations matter

Every performance test has limits. They might be:

  • Test data is not identical to production data.
  • Third-party dependencies were excluded from scope.
  • Monitoring coverage was partial.
  • The environment was shared or not perfectly stable.
  • Only a subset of user journeys was included.

Stating limitations is not a sign of weak analysis. It shows the work is honest and helps the reviewer understand how much weight to place on the evidence.

4. Recommendations

A recommendation should be specific and actionable. It should answer the practical question: “What should happen next?”

Examples include:

  • Investigate database query performance under peak load.
  • Increase thread pool capacity or tune connection pooling.
  • Refine the app workload model to include a more realistic user mix.
  • Repeat the run in a production-like environment before a release decision.

Recommendations should be grounded in the evidence, not in generic advice.

5. Final assessment rubric

  • 20%: clear scope, objectives, assumptions, and risks.
  • 25%: valid NeoLoad design and workload model.
  • 25%: repeatable execution and complete evidence.
  • 20%: accurate metric and SLA analysis.
  • 10%: practical recommendations and honest limitations.

This final evaluation is meant to judge whether the test and report are trustworthy and whether they support a real engineering decision.

Final deliverable

Submit the final performance report containing the objective, workload model, results, errors, monitoring evidence, limitations, and recommendations. Also include the supporting project files, run logs, and baseline/target comparison as appendices.
