Week 4, Day 10: REST Methods, Status Codes, Headers, and JSON

IntermediateUnderstand the language of API interaction so your load test matches real production behavior.

Session outcome

Today’s topic is foundational: the API contracts behind many modern systems. You will learn how REST methods map to intention, how status codes communicate success or failure, why headers matter for validation, and how JSON bodies hold the data the application sends and expects.

1. REST methods and what they mean

REST is an architectural style built around resources and standard HTTP operations. A resource might be an employee, a user, a product, or an order. Each operation typically maps to a clear business intent.

MethodCommon purposeTypical business meaning
GETRead dataLoad a page, fetch a list, view a record.
POSTCreate or submit new dataLogin, create a record, save a form, initiate an action.
PUTReplace or update a resource completelyUpdate a full record representation.
PATCHUpdate part of a resourceAlter selected fields, notes, metadata, or flags.
DELETERemove a resourceDelete a user, job, order, or item.

When you model a journey in NeoLoad, the method matters because it tells you the business action being performed. A POST to login and a GET to fetch employee details are not interchangeable, and their expected responses often differ.

2. HTTP status codes

Status codes are the server’s short answer to “Did the request succeed?” They also tell you whether the problem is client-side, server-side, or a business rule issue.

Common categories

  • 2xx: success—request accepted and processed.
  • 3xx: redirect or forwarding.
  • 4xx: client error—bad request, unauthorized, forbidden, not found.
  • 5xx: server error—unexpected failure or unavailable service.

Examples

  • 200 OK: normal success for GET or valid response.
  • 201 Created: resource created successfully.
  • 202 Accepted: request accepted for async processing.
  • 204 No Content: successful action without a response body.
  • 400 Bad Request: invalid input or malformed request.
  • 401 Unauthorized: missing or invalid auth.
  • 403 Forbidden: authenticated but not allowed to do this action.
  • 404 Not Found: resource does not exist.
  • 500 Internal Server Error: server unexpectedly failed.

Do not treat a 2xx status as automatically correct. You still need to assert that the response data is valid for the business case.

3. Headers and content type

Headers help the server and client agree on how the body should be interpreted. Two of the most important ones during API scripting are Content-Type and Authorization.

  • Content-Type: tells the server what format the request body uses, such as JSON or form data.
  • Authorization: carries the token or credentials required for protected endpoints.
  • Accept: tells the server which response format you want to receive.
  • Cookie: preserves the current authenticated session.

An API request can fail if the Content-Type is wrong, the Authorization header is missing, or the Accept header demands a format the server does not return. In load test design, these are as important as the URL and method.

4. JSON as the default request and response format

JSON is a lightweight, readable data format commonly used by modern APIs. Most REST APIs send and receive JSON content in request bodies and response bodies. A JSON body often contains fields like:

  • id
  • status
  • message
  • data
  • token
  • employeeId

To script a realistic API, you must know what fields are required, which ones are optional, and which values are expected to match the business case. If the contract is not known, inspect the real API docs or sample responses and write the contract down before running the load test.

5. A good API contract checklist

Before scripting a new API, document the endpoint contract in a simple table:

EndpointMethodExpected statusHeadersBodyKey JSON field
/api/loginPOST200Content-Type, Acceptusername, passwordtoken
/api/employeesGET200AuthorizationNoneitems
/api/employees/{id}PATCH200Authorization, Content-Typefield changesstatus or updatedAt

That contract is not just documentation—it is the basis for assertions and failure analysis. When your load result is under pressure, it tells you what behavior is expected and what is not.

6. Practical exercise

  1. Pick one simple API path with a read and one write action.
  2. Document the method, endpoint, headers, expected status, request content, and key JSON field.
  3. Record or build the API scenario in NeoLoad.
  4. Assert status code, response content type, and one meaningful JSON field.
  5. Replay with one user and confirm the request logic and success criteria match the application contract.

7. Common mistakes

  • Sending the wrong HTTP method: a POST mistaken for a GET leads to invalid behavior.
  • Ignoring response type: expecting JSON but receiving HTML or an error page.
  • Not validating headers: security gates can reject a request before business logic executes.
  • Reading only the first field in a JSON response: you need deeper checks for real correctness.
  • Missing API contract documentation: the test becomes guesswork and future debugging becomes difficult.
