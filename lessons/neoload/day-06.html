Week 2, Day 6: Filters, Think Time, Pacing, and NeoLoad Structure

Session outcome

Learn how to remove recording noise without removing business behavior, model realistic user pauses, control the gap between iterations, and organize the NeoLoad project so another tester can maintain it.

Use the UP_HRMS_Search_Edit_Logout path from Day 4 as the working example. Every decision must be documented so the workload remains explainable.

1. Filters: remove noise safely

A filter controls which recorded traffic is retained, excluded, or handled differently. Recording captures more than business actions: static files, analytics, advertisements, browser support calls, third-party content, and duplicate resources may appear beside the requests needed for the HRMS workflow.

The goal is not to make the script smaller at any cost. The goal is to keep traffic that represents the approved system behavior and remove traffic that would distort the workload or make results difficult to interpret.

Common filter categories

CategoryExamplesDecision
Static resourcesImages, fonts, stylesheets, and scripts.Keep if their transfer cost is part of the user experience or application load; remove only when the test scope excludes them.
Analytics and telemetryTracking pixels, analytics events, marketing tags.Usually exclude when they are outside the system under test and would add irrelevant traffic.
Third-party servicesExternal ads, maps, chat, or hosted widgets.Exclude or model separately unless the dependency is part of the agreed scope.
Browser noiseFavicon requests, extension calls, duplicate refreshes.Remove when they do not affect the business flow.
Functional requestsLogin, employee search, employee update, logout, session, token, and validation calls.Keep. These requests are part of the business journey or its correctness.

Filter decision process

  1. Identify the request by host, path, method, purpose, and response.
  2. Ask whether removing it changes authentication, data, business validation, user-visible timing, or application state.
  3. Choose keep, exclude, or investigate. Never exclude an unknown request only because its name looks technical.
  4. Replay the path after the change and compare functional results and key timings.
  5. Record the rule, reason, owner, date, and impact in the project notes.

2. Think time: model a user's pause

Think time is the pause while a user reads a page, decides what to do, enters information, or waits before taking the next action. It belongs inside the journey between user actions and usually occurs within a transaction or page flow.

Examples in the HRMS path

  • Pause after the dashboard opens while the user decides to open Employees.
  • Pause while the user reads the employee table and identifies the first record.
  • Pause while the user reviews the employee edit form before changing a field.
  • Pause after saving while the user reads the confirmation.

Think time should represent a user behavior, not server waiting. Do not add think time to hide slow response time, and do not remove every pause just to make the test run faster. If a pause is unknown, document the assumption and use a consistent value until real usage data is available.

3. Pacing: control iteration frequency

Pacing is the delay that controls how frequently a virtual user starts the next iteration of a user path. It prevents a script from looping unrealistically fast after the previous iteration finishes. Think time models pauses within a journey; pacing controls the gap between journeys.

ConceptWhere it occursPurpose
Think timeBetween actions or pages in one iteration.Models reading, decision-making, and data entry.
PacingBetween the end of one iteration and the start of the next.Controls business frequency and prevents unrealistic looping.
Load scheduleAcross the whole population or test.Controls how many users arrive, hold, and leave over time.

Example: a user may spend 20 seconds reading the Employees page, then complete the edit flow in 8 seconds, and wait 60 seconds before starting the next employee-maintenance iteration. The 20 seconds is think time; the 60-second gap is pacing.

Do not confuse pacing with throughput. Pacing is a model input; throughput is an observed result. Changing pacing changes the offered workload and can change throughput, response time, and resource utilization.

4. NeoLoad project structure

Keep the project organized by responsibility and reuse. A clear structure makes it easier to review changes, compare results, and hand the test to another engineer.

Project areaWhat belongs thereHRMS example
Project informationPurpose, owner, target environment, version, approvals, and assumptions.HRMS training target and approved test scope.
User pathsRecorded or designed user journeys with actions, pages, transactions, requests, data, and assertions.UP_HRMS_Search_Edit_Logout.
Variables and dataParameterized values, data files, extractors, correlation variables, and masking decisions.Employee identifier and current session values.
PopulationsGroups of virtual users with shared behavior, data, and load settings.HRMS employee-maintenance users.
Runtime settingsDuration, user counts, arrival rate, pacing, ramp pattern, zones, and stop conditions.One-user validation before a controlled population run.
MonitoringServer, application, database, network, and log monitoring configuration.HRMS application and data-store health during execution.
ResultsRun metadata, transaction measurements, errors, percentiles, exports, and comparison notes.Baseline and load result sets with matching configuration.

5. Practical exercise in NeoLoad

  1. Open UP_HRMS_Search_Edit_Logout from Day 4.
  2. Review every recorded item and create a filter decision: keep, exclude, or investigate.
  3. Keep login, employee search, employee update, session, correlation, validation, and logout traffic.
  4. Exclude only approved noise and document each exclusion with its reason.
  5. Add think-time assumptions between dashboard navigation, employee search, edit review, and save confirmation.
  6. Configure pacing for the gap between one completed employee-maintenance flow and the next iteration.
  7. Check that the user path, variables, population, runtime settings, monitoring, and results areas are clearly named and saved.
  8. Replay one user and verify that the filtered path still logs in, searches, saves the approved training change, and logs out.

6. Common mistakes and corrections

  • Removing all static resources: decide whether page-transfer experience is in scope before excluding them.
  • Removing session or validation traffic: the script may appear fast but no longer represents a valid user.
  • Using think time as a server wait: measure server delay separately and keep user pauses intentional.
  • Using pacing inside every transaction: this changes business response measurements; keep between-iteration pacing outside the transaction being measured.
  • Leaving default names: anonymous request names make result analysis and troubleshooting slow.
  • Mixing environments or versions: preserve the target, project version, data source, and runtime settings with every result.
