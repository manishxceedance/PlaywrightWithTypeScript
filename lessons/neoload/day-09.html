Week 3, Day 9: Assertions, Sessions, Headers, and Tokens

IntermediateCheck whether the API or page did the right thing, not just whether it responded.

Session outcome

On this day, you move from “the request returned something” to “the request produced the expected effect.” You will define the difference between status-code checks, business assertions, session continuity, header validation, and secure token handling.

1. Why assertions matter

Without assertions, a test can report success even though the application returned an error page, a validation message, empty list data, or a session-expired response. In performance testing, this is dangerous because the result becomes “green” even though the user journey failed.

Assertions answer the question: “Did the application behave as expected?” They can validate:

  • HTTP status codes, such as 200, 201, 202, 302, 401, or 500.
  • Business outcome, such as “login succeeded,” “employee row exists,” or “token was accepted.”
  • Response content or field values, such as a JSON property equal to the expected ID.
  • Expected redirect or page state after the action.

The best scripts combine both transport checks and meaningful business checks. A 200 OK with the wrong payload is not a valid success. Similarly, a 302 redirect is not enough if the user remains on the login page.

2. Sessions and cookies

Most web applications keep a user session alive with cookies, server-side state, or browser storage. In a performance test, these values are essential because they prove the requester remains authenticated and in the correct context.

Session data can be created during login, stored in cookies, or carried through the application via headers, tokens, or local state. If the session is not preserved correctly, future requests may fail even though the script reaches the right endpoint.

Common examples:

  • Session cookie after login.
  • Authentication token in a header.
  • Context-specific IDs used by the application to determine which records the user can access.

3. Headers and their role

HTTP headers tell the server information about the request and the client. Some headers are standard, such as Accept, Content-Type, and User-Agent. Some are custom or generated dynamically, such as Authorization, X-CSRF-Token, or correlation values.

If a request includes the wrong header value or omits a required header, the server may reject it even though the route is correct. This is especially common in API testing, CSRF-protected web applications, and signed or tokenized flows.

When designing checks:

  • Confirm required headers are present for the request.
  • Check Content-Type when payloads are sent.
  • Verify Authorization, Cookie, and X-CSRF-Token values are correct and current.
  • Keep header names and values consistent with the real app behavior.

4. Tokens: what they are and why they matter

Tokens are often used as short-lived security or state values. They help confirm that a request came from the right user in the right phase of the transaction. Examples include:

  • Auth token for a protected endpoint.
  • CSRF token to prevent cross-site request forgery.
  • Session token or nonce returned by a server.

If a token is stale, expired, or mismatched, the request can be rejected even when the rest of the request is valid. This is why extraction and correlation are often paired with assertions. A token that is successfully extracted but not used correctly still fails the script.

Important security rule: Never store, print, or commit real credentials, tokens, or session values in project files or public notes. Use approved test accounts and keep confidential values out of logs and exported artifacts.

5. Types of assertions you should add

Success assertions

  • Login request returns a successful authentication status.
  • Search returns at least one matching employee or expected result count.
  • Update request returns a success code and visible confirmation.
  • Logout leads back to a logged-out state.

Negative assertions

  • Invalid password should fail with a defined error.
  • Missing required field should return validation error.
  • Unauthorized request should fail with 401 or equivalent.
  • Unknown ID should return not found or a graceful error.

Negative checks are critical because they prove the application is not just returning something—it is enforcing the correct behavior when input is invalid.

6. Practical approach in NeoLoad

  1. Define the successful outcome of each critical action.
  2. Decide whether the assertion is a status check, text check, JSON field check, or redirect check.
  3. Make sure the assertion matches the real app contract, not a guess.
  4. Replay the script once with valid data and once with invalid test data.
  5. Compare the failure message and status code to the expected application behavior.

Do not create assertions that are too weak or too broad. A weak check like “any response body is returned” hides problems. A too-broad check like “error text contains login” can also be misleading. The ideal assertion is specific and meaningful.

7. Common mistakes

  • Only checking status codes: a 200 response can still be a failed business action.
  • Checking for text that changes frequently: keep the assertion stable and tied to business meaning.
  • Ignoring cookie or token flow: the request may fail even though the endpoint is correct.
  • Writing assertions only for success: negative tests are necessary to prove validation and security work.
  • Using real credentials in a test script: always use safe, approved test accounts.

Day 9 deliverable

Create a validation table for your target user flow. Include at least one valid success assertion, one negative assertion, the cookie or session element being preserved, the header or token used for the request, and a short note explaining why the assertion proves business correctness.
