Week 1, Day 2: Performance Testing and Its Types

Learning objectives

By the end of this session, you should be able to explain performance testing in plain language, identify the risk behind a test, distinguish the major performance test types, and choose a suitable NeoLoad workload for each one.

1. What is performance testing?

Performance testing is the controlled measurement of an application's speed, stability, scalability, and resource behavior under a defined workload. The workload describes what users do, how often they do it, how many users are active, how long the test runs, and what data they use.

It is different from functional testing. Functional testing asks, "Does the feature produce the correct result?" Performance testing also asks, "Does it continue to produce the correct result quickly and reliably when many users or large amounts of data are involved?"

2. Why is performance testing needed?

  • Protect user experience: slow pages and failed transactions reduce trust and completion rates.
  • Validate service levels: verify agreed response-time, throughput, availability, and error targets.
  • Find capacity limits: understand how much traffic the system can support before quality degrades.
  • Find bottlenecks early: expose limits in application code, databases, APIs, networks, queues, or infrastructure.
  • Reduce production risk: test expected peaks and failure behavior before a release or business event.
  • Support planning: provide evidence for infrastructure sizing, scaling decisions, and release readiness.
  • Detect degradation: compare a new build with a trusted baseline and identify performance regressions.

3. Important performance measurements

MeasurementDefinitionExample question
Response timeTime taken by a request or business transaction to complete.How long does login take at the 95th percentile?
ThroughputAmount of completed work per unit of time, such as requests or orders per second.How many orders can the service process per minute?
ConcurrencyNumber of users or requests active at the same time.What happens with 500 active users?
Resource utilizationUse of CPU, memory, disk, network, database connections, or other resources.Does database CPU saturate during the peak?
Error ratePercentage or count of failed requests or failed business validations.Do errors remain below the agreed threshold?
PercentileA response-time position showing the experience of most users, including the tail.Does p95 meet the service-level target?

4. Types of performance testing

These test types can be combined. For example, a capacity test may use a gradual load ramp, while an endurance test may use the normal production workload for several hours.

TypeDefinitionWhen to use itTypical NeoLoad design
BaselineA small, controlled run used as a comparison point.Before a load test, release, or tuning change.One or a few users, stable data, short duration.
LoadTesting the expected number of users and normal business traffic.To confirm the system meets targets under planned conditions.Production-like user mix, pacing, duration, and workload.
StressGradually increasing load beyond the expected level until limits or unacceptable behavior appear.To find the breaking point and observe degradation.Load zones with increasing users or arrival rate and stop conditions.
SpikeA sudden increase or decrease in workload.To test flash sales, announcements, batch events, or sudden demand.Rapid ramp-up, short peak hold, and controlled ramp-down.
Endurance / SoakRunning a sustained workload for a long period.To find memory leaks, connection leaks, queue growth, or gradual slowdown.Normal load held for hours with continuous monitoring.
VolumeTesting with a large amount of data, records, files, or payload content.To find data-size, query, storage, or processing limits.Controlled data set with realistic record and payload sizes.
CapacityDetermining the maximum workload that meets defined performance targets.For infrastructure sizing and business growth planning.Stepwise load increase until the first agreed SLA fails.
ScalabilityMeasuring how performance changes when resources or workload are increased.To validate horizontal or vertical scaling decisions.Repeatable tests across instance counts, zones, or resource sizes.
Failover / RecoveryMeasuring behavior during component failure and recovery.To validate resilience, continuity, and recovery objectives.Approved fault event, monitored workload, recovery timing, and data checks.
ConcurrencyTesting many simultaneous actions or requests competing for shared resources.For checkout, reservations, updates, locking, or shared inventory.Coordinated virtual users performing the same operation together.

5. How to choose the right type

  1. Start with the risk: slow normal traffic, sudden demand, long-running stability, large data, or failure recovery.
  2. Define the workload: users, arrival rate, user mix, pacing, data, duration, and environment.
  3. Define success: response-time percentile, throughput, error rate, resource limit, or recovery time.
  4. Choose the smallest test that can answer the question, then increase scope only when the evidence is valid.

Example: If the risk is a year-end traffic surge, use a load test for expected traffic and a spike test for the sudden increase. If the risk is a memory leak, use an endurance test. If the risk is slow searches with millions of records, use a volume test.

Use the published Login - HRMS Practice App as the sample system from Day 1.

  1. Create a decision table with these columns: risk, test type, workload, duration, success criteria, and evidence.
  2. Add at least six rows covering baseline, load, stress, spike, endurance, and volume testing.

  4. Open NeoLoad and describe which user path, population, pacing, and runtime settings you would configure for each row.
