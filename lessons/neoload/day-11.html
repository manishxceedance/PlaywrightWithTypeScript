Week 4, Day 11: Authentication and Request Chaining

IntermediateBuild realistic API flows where one response unlocks the next request.

Session outcome

Modern APIs are rarely a single isolated call. Most user journeys begin with authentication, then fetch data, then create or update an entity, then validate the final state. This day focuses on chaining: using a value from one response as the input to a later request.

1. Why chains matter

A performance test is only realistic if it models real dependencies. In a real application, a login call usually returns a session token, a user collection, a user profile, or an auth context. The next request often depends on that value. If the script does not chain values correctly, it will not represent the application’s real behavior.

Examples include:

  • Login returns a token, which is then sent as an Authorization header.
  • Search or list API returns an ID, which is then used to fetch the item details.
  • Resource creation returns an ID, which is then used to verify retrieval or update the created object.
  • Session creation and user state validation ensure the user is proceeding in a valid context.

2. Authentication patterns

Different applications use different auth patterns. The most common include:

  • Session cookie: the server issues a session identifier after login; later requests send the cookie.
  • Bearer token: login returns a token, and later requests send Authorization: Bearer ....
  • API key or custom header: some systems send a key or signature in headers.
  • Signed request body or nonce: highly secured systems use nonce or encrypted values in each request.

Whatever the mechanism, the same principle applies: capture the value from the correct response and reuse it in subsequent requests without hard-coding or reusing a stale value.

3. The flow of a chained API journey

A realistic API flow often looks like this:

  1. Authenticate with approved credentials.
  2. Capture the returned token or session identifier.
  3. Call a protected endpoint using the captured value.
  4. Capture a returned record ID or business value from the response.
  5. Use that ID in a subsequent read or update request.
  6. Validate the final state and then complete the transaction.

This is where many scripts fail. The test engineer knows the endpoints, but not the dependency chain. The script reaches the login step but sends an old token or an empty ID, causing downstream failures.

4. Request chaining in NeoLoad

Request chaining means the value from one request becomes the input for another. NeoLoad makes this possible through extractors, variables, and parameterization. In a typical setup:

  • Login request extracts authToken.
  • Protected GET request uses ${authToken} in the Authorization header.
  • List or create response extracts employeeId.
  • Update request sends ${employeeId} in the path or body.

A well-designed chain should be easy to read. If a tester cannot tell where the ID came from and which request consumed it, the script is not maintainable.

5. Authentication security rules

Do not hard-code production secrets or tokens into your performance scripts or project notes. Use approved test users and environment-specific credentials only. Keep configuration values in secure, managed locations and mask sensitive details in logs and reports.

Even in non-production or training environments, the same practice matters. A script that leaks credentials is a security risk and can create a false sense of protection around personal data.

6. Debugging chain failures

When a chain fails, the fix usually sits in one of three places:

  • The token was not extracted at all.
  • The wrong value was extracted from the wrong response.
  • The value was extracted correctly but used in the wrong field, header, or later stage.

Always inspect the response order. Make a quick map of “request A creates value X, request B requires value X.” If the chain breaks anywhere in between, the script will fail at a later stage.

7. Practical exercise

  1. Choose one authenticated workflow, such as login + fetch employee + update employee.
  2. Document each request and the value it creates or consumes.
  3. Extract the auth token or session value from the login response.
  4. Use that value in the protected request and verify the response succeeds.
  5. Capture a returned entity ID and use it in the next request.
  6. Validate the final state and record the chain in a dependency diagram.
